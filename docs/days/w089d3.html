Week 89, Day 3

Build

“The best route” depends on who’s walking. Someone with a pushchair wants to avoid steep climbs; someone walking a dog wants to keep off roads; someone short of time wants the shortest. Today’s story, S9, walking preferences, turns the route search from “shortest” into “cheapest” by a cost that the preferences define: roads can count three times their length, steep uphill sections twice. The search doesn’t change at all: Dijkstra’s algorithm finds the cheapest route for any cost that’s never negative. You’ll model preferences as a validated, immutable value parsed from a query string, compute costs, find the best route, explain it in plain words, and, in the challenge, offer a few genuinely different alternatives with honest labels.

By the end of today you can

  • Model options as a frozen dataclass that validates itself, parsed from a query string
  • Express preferences as a cost per path, and find the cheapest route with an unchanged search
  • Explain a route’s choices in plain words
  • Offer distinct alternatives and label them honestly
  • Keep the search generic, and the policy in one place

waymark_domain.py
import heapq


class UnknownPlace(LookupError):
    pass


class NoRoute(Exception):
    pass


def naismith_minutes(km, climb_m):
    return round(km / 5 * 60 + climb_m / 600 * 60)


class Route:
    def __init__(self, stops, km, climb_m):
        self.stops, self.km, self.climb_m = list(stops), km, climb_m

    @property
    def minutes(self):
        return naismith_minutes(self.km, self.climb_m)

    def __repr__(self):
        return f"Route({self.stops}, {self.km} km, {self.climb_m} m)"


class PathNetwork:
    def __init__(self, heights):
        self.heights = dict(heights)
        self.paths = {name: {} for name in self.heights}

    def _check(self, *names):
        for name in names:
            if name not in self.heights:
                raise UnknownPlace(name)

    def add_path(self, a, b, km):
        self._check(a, b)
        if km <= 0:
            raise ValueError("km must be positive")
        self.paths[a][b] = km
        self.paths[b][a] = km

    def climb(self, stops):
        return sum(max(0, self.heights[b] - self.heights[a]) for a, b in zip(stops, stops[1:]))

    def shortest(self, start, end):
        self._check(start, end)
        dist, prev, done = {start: 0}, {}, set()
        heap = [(0, start)]
        while heap:
            d, node = heapq.heappop(heap)
            if node in done:
                continue
            done.add(node)
            if node == end:
                break
            for nxt, km in sorted(self.paths[node].items()):
                if d + km < dist.get(nxt, float("inf")):
                    dist[nxt] = d + km
                    prev[nxt] = node
                    heapq.heappush(heap, (d + km, nxt))
        if end not in done:
            raise NoRoute(f"no route from {start} to {end}")
        stops = [end]
        while stops[-1] != start:
            stops.append(prev[stops[-1]])
        stops.reverse()
        return Route(stops, round(dist[end], 2), self.climb(stops))

from waymark_domain import PathNetwork

HEIGHTS = {"Mill": 40, "Weir": 55, "Church": 80, "Ridge": 310, "Farm": 120, "Wood": 150, "Lake": 60, "Island": 5}

def sample_network():
    network = PathNetwork(HEIGHTS)

waymark_kinds.py
KINDS = {
    frozenset({"Mill", "Church"}): "road",
    frozenset({"Lake", "Mill"}): "road",
    frozenset({"Weir", "Farm"}): "track",
    frozenset({"Wood", "Lake"}): "track",
}


def kind_of(a, b):
    """The kind of the path between two junctions: road, track, or (by default) path."""
    return KINDS.get(frozenset({a, b}), "path")

Warm-up

The shortest route to Ridge finishes with a climb of 190 m in 2 km. For a walker who wants to avoid steep sections, a slightly longer route might be better; for one who wants to keep off roads, this one is fine. The map file of Week 88 gains a kind for each path; open waymark_kinds.py above to see the sample’s.

Cost, not just distance

Dijkstra’s algorithm never cared that the numbers on the paths were kilometres: it finds the route with the smallest sum of costs, for any costs that aren’t negative. So preferences become a cost function: for each step from a to b,

  • start with the distance;
  • multiply by a road factor (say 3) if the walker avoids roads and the path is a road: a road counts as three times as long, so it’s used only when the alternative is more than three times longer;
  • multiply by a steep factor (say 2) if the walker avoids steep climbs and this step climbs more than the steep limit (say 80 m per km). Only uphill counts: the cost is per direction.

The search returns the cheapest route; the reported distance and time are still the real ones. Keeping the search generic and putting the policy in one cost function means a new preference (avoid fields with cattle, prefer shade) changes one function, not the algorithm.

Preferences as a value

Preferences arrive as a query string (?avoid=roads,steep&steep_limit=80) and travel through the service to the search. Model them as a frozen dataclass (Week 32): immutable (so a cached result keyed by them can’t be corrupted), comparable, printable, and validating itself in __post_init__, so an invalid set of preferences can’t exist. Parse the query string in a class method, Preferences.from_query(...), which raises ValueError with a clear message for anything unknown: an API answers that with 400.

The cheapest route

The search is Dijkstra with cost(a, b) in place of paths[a][b]. Track the real distance alongside the cost (or recompute it from the stops) so the route reports kilometres, not cost units. One subtlety: costs must never be negative, which multiplication by factors of at least 1 guarantees, and which the preferences’ validation enforces.

Explaining and offering choices

A route that’s longer than the obvious one needs a reason, or users assume it’s a bug. Explain the route in plain words: how far on roads, how many steep sections and where, and how much longer it is than the shortest. Better still, offer a few alternatives (the shortest, the flattest, the quietest), each labelled, and merge identical ones: if the shortest route is also the quietest, show it once as “shortest and quietest” rather than three identical lines.

Key idea

Searches find the cheapest route for any non-negative cost, so express preferences as a cost per step (distance times factors for roads or steep uphill sections) and leave the search unchanged. Report real distances and times, not costs. Model preferences as a frozen dataclass that validates itself, parsed from the query string with clear errors. Explain why a route was chosen, and offer distinct alternatives with merged, honest labels.

Bug hunt10 points
Downhill counted as steep

The steepness check uses the size of the height change, so walking down from the ridge counts as a steep climb: it prints steep: True. Count only climbing, so it prints steep: False.

Bug hunt10 points
A list as a dataclass default

Dataclasses refuse a mutable default (one list shared by every instance), so this crashes with ValueError: mutable default <class 'list'> for field avoid is not allowed. Use field(default_factory=list), so it prints [] ['roads'].
