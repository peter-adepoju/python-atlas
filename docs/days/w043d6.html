Week 43, Day 6Forge day

Forge

This week was about structures that only let you work at the ends: stacks (last in, first out), queues and deques (first in, first out, and both ends), monotonic stacks and deques for nearest-bigger questions and window maximums, stacks that parse and evaluate expressions, and circular buffers that never move anything. Today’s Forge is a print shop’s job system that uses several of them together: a ring of waiting jobs that urgent jobs can jump to the front of, an undo stack, a history that keeps only the latest jobs, and a small command interface. The bonus is two classic problems that need a monotonic stack and a monotonic deque.

By the end of today you can

  • Choose the right end-only structure for each part of a system
  • Combine a ring deque, a stack and a bounded history in one class
  • Undo safely, refusing when the world has moved on
  • Use monotonic stacks and deques to answer harder questions in O(n)

A possible pop order?

pushed lists distinct values in the order they were pushed onto an empty stack, and popped lists the same values in some order. Write possible(pushed, popped): could popped be the order they came off, if pops can happen at any time between pushes? Simulate with a real stack: push each value, then pop while the top is the next value expected.

Remove k digits

Write smallest_after_removing(number, k): remove exactly k digits from the string number to leave the smallest possible number, returned as a string without leading zeros ("0" if nothing is left). Use a monotonic stack: while the last kept digit is bigger than the next digit and removals remain, remove it.

Forge: a print shop

A small print shop takes jobs from customers. Jobs wait in a queue; an urgent job jumps to the front; the printer takes jobs from the front; a customer who changes their mind can undo their last submission, if it hasn’t been printed yet; and the screen shows the last few jobs printed. Build PrintShop(capacity=8, keep=5).

Storage. Waiting jobs are job ids in a ring deque on a fixed block of capacity slots (Day 5): normal jobs join the back, urgent ones the front. A dictionary maps each id to its (name, pages). Printed ids go into a ring log of the last keep jobs (it may overwrite the oldest). Each submission is pushed onto an undo stack as (id, end), where end is "front" or "back".

Operations.

  • submit(name, pages, urgent=False): pages must be a whole number of at least 1 (else ValueError); a full queue raises OverflowError("queue is full"). Returns the new id: "J1", "J2", … (ids are never reused, even after an undo).
  • print_next(): removes the front job and returns (id, name, pages); nothing waiting raises IndexError("nothing to print").
  • undo(): pops the undo stack. If that job is still waiting at the end it was added to, remove it and return its id. Otherwise (it’s been printed), return None. With nothing to undo, return None.
  • waiting(): the waiting ids, front to back. recent(): the printed ids, newest first (up to keep). len(shop): how many are waiting.

Interface. handle(line, shop) returns a reply:

Line Reply
submit NAME PAGES queued J1
urgent NAME PAGES queued J2 at the front
print printed J2 poster (3 pages)
undo removed J1, or nothing to undo
queue queue: J3 J1 (front first), or queue: empty
recent recent: J2 J5 (newest first), or recent: none

PAGES is read with int; any ValueError, OverflowError or IndexError from the shop becomes error: and its message; anything else gets unknown command.

Exercise50 points
Forge: a print shop

Write PrintShop and handle to the specification above.

Undo that knows its limits

Week 36’s undo assumed nothing else changes the document between a command and its undo. Here the printer works on the queue too, so undo can’t blindly reverse: it checks that the world still looks the way it left it (the job is still waiting, at the end it joined) and refuses otherwise. That’s the honest version of undo in any shared system: an undo is a request, not a guarantee, and it must check before it acts (Week 37’s defensive programming). Notice also how little each structure had to do: the ring only ever touches its two ends, the undo stack only its top, the history only overwrites its oldest slot. Every operation is O(1), and the restrictions are what make that possible.

Forge bonus: two classics

Exercise30 points
Forge bonus: two classics
  1. The sum of the minimums. Write sum_of_minimums(nums): the sum, over every run of consecutive items (every subarray), of that run’s smallest item. Do it in O(n) with monotonic stacks: each item nums[i] is the minimum of exactly left[i] * right[i] runs, where left[i] is how far you can go left before meeting a strictly smaller item, and right[i] how far right before meeting a smaller or equal one (counting i itself each way). Treating ties differently on the two sides makes sure each run is counted once.
  2. A queue with a maximum. Write MaxQueue with enqueue(x), dequeue() (raising IndexError when empty), max() (raising IndexError when empty) and __len__, all O(1) amortised: keep the items in one deque, and a second, monotonic deque of candidates for the maximum, whose front is the current maximum.
