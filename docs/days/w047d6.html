Forge

This week was about heaps: the binary heap in a list with sift-up and sift-down, O(n) heapify, Python’s heapq with tie-breakers, max-heaps and lazy deletion, heap sort, top-k with a heap of size k, the running median, and k-way merging with a frontier. Today’s Forge puts them to work in an event-driven simulation of a small computing cluster: jobs arrive, wait by priority, get cancelled, run on machines and finish, all ordered by heaps. The bonus merges log files from several servers into one timeline without reading any of them whole. The weekly quiz and review finish the week.

By the end of today you can

  • Drive a simulation from a heap of timed events, with clear rules for simultaneous events
  • Combine several heaps (events, waiting jobs, free machines) with lazy cancellation
  • Answer top-k questions about the results
  • Merge sorted files lazily, refusing bad lines without stopping

Mixed review

Exercise10 points
Smashing stones

You have stones of given weights. Each turn, take the two heaviest; if they’re equal both are destroyed, otherwise the lighter is destroyed and the heavier loses the lighter’s weight. Write last_stone(weights): the weight of the last stone left, or 0 if none, using a heapq max-heap (negated weights). Then turns(weights): how many turns that takes.

Exercise10 points
Joining ropes

Joining two ropes of lengths a and b costs a + b and makes one rope of length a + b. Write cheapest_join(lengths): the least total cost to join all the ropes into one. Always joining the two shortest ropes is optimal (the same greedy idea as Huffman coding in Week 45), so use a min-heap. Then join_order(lengths): the list of (a, b) pairs joined, in order, with a <= b.

Forge: a cluster simulator

A small computing cluster has machines identical machines, numbered from 0. Jobs arrive over time, each with a duration and a priority (smaller is more urgent). Build an event-driven simulation: rather than ticking a clock minute by minute, keep a heap of future events and jump from one to the next.

Write Cluster(machines) (ValueError if fewer than 1) with:

  • submit(time, name, duration, priority): a job named name will arrive at time. Raise ValueError for a name already submitted, a negative time or a duration that isn’t positive.
  • cancel(time, name): at time, if the job is waiting (arrived and not started), it’s removed and never runs; otherwise (not yet arrived, running, finished, or unknown) nothing happens.
  • run(): simulate everything and return the log, a list of (time, what, name, machine) tuples, where what is "start", "finish" or "cancel" (with machine None for a cancel).

The rules, which decide every tie:

  1. Events at the same time are handled in this order: all finishes (in machine-number order), then all cancellations, then all arrivals (cancellations and arrivals each in the order submit and cancel were called). So a job that finishes at 5 frees its machine for a job that arrives at 5, and a cancellation at 5 can’t touch a job arriving at 5.
  2. After all the events at one time have been handled, dispatch: while a machine is free and a job is waiting, start the most urgent waiting job (smallest priority, then earliest arrival, then name) on the lowest-numbered free machine. It finishes at the current time plus its duration.

After run():

  • waits(): a dict from each job that started to how long it waited (start minus arrival);
  • busiest(k): the k machines with the most total running time, as (machine, busy_time) pairs, busiest first, ties to the lower number;
  • longest_waits(k): the k longest waits as (name, wait) pairs, longest first, ties alphabetical.

Use heaps for everything that needs a “next”: the events, the waiting jobs (with lazy deletion for cancellations) and the free machines. The checks compare you with a simple minute-by-minute simulation on random workloads, and run 20,000 jobs on 8 machines.

Exercise50 points
Forge: a cluster simulator

Write Cluster to the specification above.

Rules for ties

Most of the specification is about ties: what happens when a job finishes at the same moment another arrives, which of two equally urgent jobs goes first, which free machine gets the job. A simulation without these rules still runs, but two correct-looking programs give different answers, and nobody can say which is right. Writing the rules down, and encoding them in the heap entries themselves (kind before counter, priority before arrival before name), is what makes the simulation deterministic: the same input always gives the same log, which is what lets the checks compare you with a completely different simulation. The same thinking applies whenever you use a heap: decide what decides a tie, and put it in the tuple.

Three servers each write a log file, one line per event: a timestamp like 2026-11-02T10:00:03, a level (DEBUG, INFO, WARNING or ERROR), and a message, separated by single spaces (the message may contain spaces). Each file is in time order, but real logs have junk in them.

Exercise30 points
Forge bonus: merging server logs

Write:

  • merge_logs(paths, dst): merge the files into dst as one timeline, each line written as timestamp source level message, where source is the file name without .log. Equal timestamps keep the order of paths. Skip, and count, bad lines: anything without three parts, a timestamp not in exactly the form YYYY-MM-DDTHH:MM:SS (use a regular expression), an unknown level, or a timestamp earlier than the previous good line in the same file (which would break the merge’s order). Blank lines are skipped without counting. Return the number of bad lines. Read every file lazily, one line at a time, with a heap of one entry per file (write an iterator class for reading a file’s good lines); never call read() or readlines().
  • top_errors(path, k): from a merged file, the k most common ERROR messages as (message, count), most common first, ties alphabetical.
  • busiest_minute(path): from a merged file, the minute (the first 16 characters, like 2026-11-02T10:00) with the most lines, the earliest on a tie; None for an empty file.
