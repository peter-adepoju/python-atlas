How to review

The same rules as Phase 1’s review week, because they’re the ones that work:

  1. Try every prediction before running it, and write your guess down.
  2. When a guess is wrong, find exactly why before moving on.
  3. Keep a list of everything that surprised you. That list is your revision plan for Friday’s exam.

The method

Week 14’s method for any problem you haven’t seen before, in four steps:

  1. Understand it: restate it in your own words, and work two or three examples by hand, including an awkward one.
  2. List the edge cases: empty input, one item, ties, boundaries, invalid input. Decide what should happen for each.
  3. Plan in pseudocode or a list of steps before writing Python, and pick the patterns that fit (counting, finding the best, building a result, grouping).
  4. Decompose: split the work into small functions, each with one job, and test each one as you go.

The “finding the best” pattern with a running counter. The empty string and the all-losses string are the edge cases worth checking; both give 0 because best starts at 0.

Key idea

Understand, list the edge cases, plan, decompose. Work examples by hand before writing code, and decide what the edge cases should do before you meet them.

Recursion: the essentials

A recursive function solves a problem by calling itself on a smaller version of the same problem. Every correct one has:

  • a base case: an input small enough to answer directly, without recursion;
  • a recursive case that makes progress: each call moves closer to the base case;
  • trust: assume the smaller call returns the right answer, and build yours from it.

Each call gets its own frame on the call stack, with its own variables. Calls go down until a base case returns, then the answers come back up, each waiting call finishing its own work with the value it gets.

Code before the recursive call runs on the way down; code after it runs on the way back up, in reverse order.

Python stops recursion that goes about 1000 calls deep with RecursionError. That’s why a loop is usually better for simple counting down a long list, and recursion is best where the problem itself branches or nests (Week 15, Day 5).

Key idea

Base case, progress, trust. Each call has its own frame; work before the call happens going down, work after it coming back up. Very deep recursion raises RecursionError, so loops suit long straight runs and recursion suits nesting and branching.

Recursion on data

Recursion fits data that contains smaller versions of itself: a list is its first item plus a smaller list; a nested list contains lists; a folder contains folders.

Divide and conquer splits the problem into halves, solves each half, and combines the answers: merge sort (Week 16, Day 1, and Week 19) is the famous example. Halving means only about log₂(n) levels of calls, so it never gets near the recursion limit.

Tree recursion and memoisation

When a function calls itself more than once, the calls form a tree, and the number of calls can grow exponentially:

177 calls to work out the 10th Fibonacci number, because the same small calls are repeated again and again. Memoisation stores each answer the first time it’s worked out, and looks it up after that. functools.cache does it for you:

Tree recursion also generates things: every subset (each item is either in or out: 2ⁿ of them) or every permutation (each item can come first, then permute the rest: n! of them).

Key idea

Several recursive calls make a tree; repeated subproblems make it exponential, and memoisation (@cache) removes the repeats. Subsets come from “in or out” for each item; permutations from “each item first, then the rest”.

The classic mistakes

  1. No base case, or one that’s never reached: RecursionError. Check that every path makes progress towards it: n - 2 from an odd number jumps straight past a base case of n == 0.
  2. Forgetting to return the recursive call’s result: f(n - 1) + n without return gives None.
  3. A mutable default argument used as an accumulator (def walk(x, out=[])): the same list is shared by every call to the function, so results pile up from one call to the next. Use out=None and create the list inside.
  4. Ignoring the result of a recursive call that returns a new value: flatten(item) on its own line does nothing useful.
  5. Exponential tree recursion where memoisation, or a loop, is needed.
  6. Slicing in every call on very long lists: xs[1:] copies the list each time, making a simple recursive sum O(n²). Fine for exercises; pass an index instead when it matters.

Digit sum, recursively

Write digit_sum(n) for a whole number n of 0 or more, without loops (no for or while): digit_sum(4096) is 19, digit_sum(0) is 0.

Exercise10 points
Palindromes

Write is_palindrome(text) recursively, ignoring case and anything that isn’t a letter or digit: "Never odd or even" is a palindrome. Clean the text once, then recurse on the cleaned text with a helper. No loops except in the cleaning.

Exercise10 points
How deep?

Write depth(x): a value that isn’t a list has depth 0; a list has depth 1 more than its deepest item (an empty list has depth 1). depth([1, [2, [3]], 4]) is 3.

Exercise15 points
Ways to pay

Write ways(amount, coins): how many different ways can you make amount pence from coins of the given values (as many of each as you like)? Order doesn’t matter: 1+2 and 2+1 are the same way. ways(5, (1, 2, 5)) is 4. It must handle ways(300, (1, 2, 5, 10, 20, 50, 100, 200)) quickly.

Exercise15 points
Subsets that add up

Write subsets_with_sum(items, target) returning every subset (as a list, keeping the items’ original order) whose sum is target, in the order the “leave the first item out, then put it in” recursion finds them. subsets_with_sum([3, 1, 2, 4], 5) is [[1, 4], [3, 2]].

Exercise15 points
Every arrangement

Write arrangements(word) returning every different arrangement of the letters of word, sorted. arrangements("aab") is ["aab", "aba", "baa"]. Write the recursion yourself (no itertools).
