Week 97, Day 6

Mock loop

An interview loop is several rounds in a row, often four or five in one day, each with a different interviewer: coding, design, code review, behavioural. Stamina and switching between kinds of thinking are part of the test. Today is your first mock loop, compressed: warm-up predictions, two quick review problems, a forty-minute coding round (a classic: a least-recently-used cache), a design question to think through aloud, and, as the bonus, the scorecard a panel uses to turn four rounds into one decision.

By the end of today you can

  • Sit several kinds of round back to back
  • Build an O(1) least-recently-used cache under time
  • Talk through a design question with numbers
  • Understand how a panel turns rounds into a decision
  • Review the week’s methods

Warm-up

Mixed review

Exercise10 points
The best k-day stretch

Write best_stretch(km, k): the largest total of any k consecutive values in km (a walk log’s daily distances), in linear time; 0 if there are fewer than k values.

Exercise10 points
One more review fix

This function reads a settings file but hides every error and leaves the file open. Rewrite read_limit(path) to return the limit from the JSON file, using with, returning 100 only when the file doesn’t exist.

Coding round

Forty minutes, one problem, out loud: clarify, examples, a simple version, the better one, code, test, complexity. Start the timer.

Exercise50 points
Coding round: a least-recently-used cache

Write a class LRUCache(capacity) with get(key) (the value, or -1 if absent) and put(key, value). Both count as using the key. When a put adds a new key to a full cache, first remove the least recently used key. Both operations must be O(1): the checks time a million operations. Also give it keys(), returning the keys from least to most recently used.

Design round

Design round: a cache in front of the Waymark API

Fifteen minutes, aloud. Waymark has 2 million users who each plan 3 routes a day; planning a route costs 40 ms of server time, and 30% of plans are for the same 1,000 popular routes. Estimate the peak requests per second (peak factor 4), how many servers you’d need at 25 plans a second each with 30% headroom, and what an LRU cache of the popular routes would save. Then the trade-offs: how stale may a cached route be when a path closes, and how would you invalidate it?

Bonus: the scorecard

After a loop, interviewers rate each round against a few criteria and meet to decide together. Simulating the decision teaches you what each round is really scoring.

Exercise30 points
Bonus: from rounds to a decision

Write loop_decision(rounds): each round has name and scores, a dict of criteria to ratings from 1 to 4. A round’s signal is its mean rating: "strong yes" from 3.5, "yes" from 2.75, "lean no" from 2, else "no". Return (lines, decision): lines "NAME: MEAN (SIGNAL)" with the mean to 2 decimal places, then "overall: MEAN" (the mean of the round means, 2 places). The decision is "no offer" if any round is "no" or two or more are "lean no"; otherwise "offer" if the overall mean is at least 3 and at least one round is "strong yes"; otherwise "another round".
