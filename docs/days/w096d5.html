Week 96, Day 5

Writing it up

Three weeks of open source have produced pull requests, reviews and a lot of learning that will fade unless you write it down. A write-up does three jobs: it’s a record for you, evidence for anyone reading your portfolio, and help for the next newcomer, who’ll search for exactly the problems you had. Today you’ll keep a structured contribution log, turn it into a table and honest numbers, link every reference properly, write a one-line summary for a CV or portfolio, and generate the skeleton of a post you’ll finish in your own words.

By the end of today you can

  • Keep a structured log of contributions and reviews
  • Turn the log into a table and honest numbers
  • Link issues and pull requests so readers can follow them
  • Summarise contributions in one accurate line
  • Write a post that helps the next newcomer

Warm-up

Five entries: three merged pull requests, one still open, and a review. A review counts: it’s real work for a real project, and many people never do one. contrib_log.py is an example log; yours will look different.

Why write it up

Memory is generous to the past: in six months you’ll remember the merge, not the three review rounds that taught you how CPython’s tests are organised. A write-up records what actually happened, which is what makes it useful to others: “how I got my first pull request into CPython” posts are read by thousands of people about to try. And in a portfolio, a link to a merged pull request, with a sentence on what it fixed, is concrete evidence of exactly the skills this phase was about.

Honest numbers

Numbers make a write-up concrete, and honest ones make it trustworthy: three merged pull requests, one open, one review; a median of nine days from opening to merge; one pull request needed three rounds of review. Don’t inflate (a typo fix is a typo fix, and that’s fine) and don’t hide the open or closed ones: a pull request that was declined, and why, is often the most interesting part. Link everything, so readers can check: gh-140101 as a link to the issue, #140188 as a link to the pull request.

A post worth reading

A useful structure: what you did (the table), how it went (one paragraph per contribution: the problem, the fix, what review taught you), what you’d tell a newcomer (the specific, practical things: “build CPython before choosing an issue”, “reviewers asked for subTest”), and what next. Specifics beat generalities; the mistakes are the most useful part. Publish it where people look (your own site, a blog, the project’s discussion forum if it welcomes such posts) and link it from your portfolio page.

Key idea

Keep a structured log as you go: project, kind, issue, PR, dates, status, review rounds. Report honest numbers (merged, open, declined, reviews, median days to merge) and link every issue and PR. Summarise in one accurate line for a CV. Write the post for the next newcomer: what, how, specific advice, what next; mistakes included.

Practice

Exercise10 points
The log as a table

Write log_table(log): a Markdown table with the header | Project | Kind | Pull request | Title | Status |, the separator |---|---|---|---|---|, and a row per entry with the PR written #N. Escape any | in a title as \|. Return the lines joined by newlines.

Exercise15 points
Honest numbers

Write contribution_stats(log, today): return a dict with pull_requests (entries that aren’t reviews), merged, open, reviews, kinds (a dict from kind to count for the pull requests, in alphabetical order), median_days_to_merge (over merged entries, in the g format as a string, or "-"), most_rounds (the title with the most review rounds, first on ties, or None) and longest_open_days (days from opening to today for the longest-open open entry, or 0).

Exercise10 points
Links readers can follow

Write link_refs(text, repo): replace each gh-N with [gh-N](https://github.com/REPO/issues/N) and each #N (a # not preceded by a letter, digit or [, followed by digits) with [#N](https://github.com/REPO/pull/N).

Exercise10 points
One accurate line

Write cv_line(log): for each project with merged pull requests (in order of first appearance), "N merged pull request(s) to PROJECT (KINDS)", KINDS the distinct kinds of its merged pull requests in order of first appearance, written docs, tests and a bug fix (joined with ", " and a final " and "); join projects with "; "; then add "; R review(s)" if there are reviews. Use the singular for 1.

Exercise15 points
The post’s skeleton

Write post_outline(log): Markdown lines joined by newlines: # What I contributed, a blank line, ## What, a blank line, then for each pull request (not reviews) a bullet - KIND: TITLE (#PR, STATUS); a blank line, ## How it went, and for each pull request a ### TITLE heading followed by a blank line and _N round(s) of review._ (singular for 1), with blank lines between; then a blank line, ## What I'd tell a newcomer, a blank line and -; then a blank line, ## What next, a blank line and -.

Bug hunt10 points
A median that included the unmerged

Open pull requests have no merge date, so date.fromisoformat(None) raises. Only use merged entries, so this prints 9.

Bug hunt10 points
A title that broke the table

A | in a title starts a new column, so the row has six cells instead of five and this prints 6. Escape it as \| so it prints 5.
