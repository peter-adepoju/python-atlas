Week 82, Day 6Forge day

Forge

This week went beyond one machine: clocks and consensus, observing a system you can’t see inside, keeping it reliable when its parts fail, and two complete design practices. Today’s Forge is a design problem where many people want the same scarce thing at the same moment: booking seats for a popular concert. It’s a favourite because a naive design sells the same seat twice. You’ll build the core the way real booking systems work: seats held for a few minutes while someone pays, holds that expire by themselves, all-or-nothing reservations, purchases that are safe to retry, and counts that never go wrong. The bonus puts a virtual waiting room in front of it, so a rush of a hundred thousand people becomes an orderly queue.

By the end of today you can

  • Turn a booking brief into the rules that stop a seat being sold twice
  • Hold seats with a time to live, so abandoned checkouts free them automatically
  • Make holds all-or-nothing and purchases idempotent
  • Admit a rush of users through a fair, first-come waiting room
  • Connect this week’s ideas (ordering, observability, reliability, rate limits) in one design

Forge: seat booking

A concert goes on sale at 10:00 and 80,000 people try to buy 20,000 seats. The rules a booking system must never break are short: a seat is sold at most once, and someone who paid gets their seats. Everything else follows from them.

  • Holds. Choosing seats and paying takes minutes, so the system holds the chosen seats for that person (ten minutes, say) and shows them to nobody else. A hold that isn’t paid for expires on its own, so abandoned checkouts free their seats without anyone cleaning up.
  • All or nothing. Four friends want four seats together. If any one of them is taken, the hold fails and none are held, otherwise the system fills up with useless fragments of groups.
  • Atomic claims. Two people clicking the same seat at the same instant must not both get it. In a real system the claim is one atomic step (a conditional write, like Wednesday’s rate-limiter store: “set this seat’s holder only if it’s free”); here, one method call does the whole check-and-claim.
  • Idempotent purchase. The payment page times out and the browser retries. An idempotency key (Week 77) makes the retry return the same order instead of charging twice.

Build BookingService(clock, hold_ttl=600, max_seats=6):

  • add_event(event_id, seats) with a list of seat ids; a repeated id raises ValueError("event exists").
  • hold(event_id, user, seats) returns a hold id ("h1", "h2", …). It raises ValueError("choose 1 to N seats") (N being max_seats) for an empty list or too many, ValueError("unknown seat X") for the first seat (in the order given) not in the event, and ValueError("seat X is taken") for the first seat that is sold or held by an unexpired hold (a user’s own hold counts too). Holds expire hold_ttl seconds after they were made (a hold is expired when now >= expires). All seats are held or none.
  • release(hold_id) cancels a hold (an unknown or finished hold is ignored).
  • purchase(hold_id, user, key): if key was used before, return the earlier order unchanged. Otherwise an unknown hold raises KeyError("no such hold"); another user’s hold raises PermissionError("not your hold"); an expired or released hold raises ValueError("hold expired"). On success the seats are sold, the hold is finished, and it returns an order {"order": "o1", "event": ..., "user": ..., "seats": [sorted seat ids]} (numbered "o1", "o2", …).
  • available(event_id): the sorted seats neither sold nor held by an unexpired hold. stats(event_id): {"sold": n, "held": n, "available": n} (seats, not holds).

Where each day’s idea appeared

Look back at your booking service. Monday’s lesson is why the holds have ids and an order of events is decided in one place, not by the buyers’ clocks; with several servers, the atomic claim would be a conditional write to the seat’s partition, and a purchase that also takes a payment is a saga (hold, charge, confirm; release the hold if the charge fails). Tuesday’s observability would count holds made, expired and purchased: a sudden rise in expired holds means the payment page is broken. Wednesday’s reliability decides what happens when the payment provider is slow: a deadline shorter than the hold’s time to live, and a circuit breaker so the queue of buyers doesn’t wait on a dead dependency. Thursday’s rate limiter stops a script holding every seat. Which rule would you break first if the venue said “seats must never sit held for ten minutes while real fans can’t see them”?

Forge bonus: a waiting room

At 10:00 the booking service could take perhaps 2,000 buyers at once; 80,000 arrive. Letting them all in makes the site slow for everyone, and the fastest scripts win. A virtual waiting room puts arrivals in a first-come queue and admits them in batches as active buyers finish, so the service runs at a pace it can sustain and the order is fair.

Exercise30 points
Forge bonus: a waiting room

Write a class WaitingRoom(clock, capacity, session_ttl). join(user) puts a new user at the back of the queue (a user already waiting or active keeps their place) and returns status(user). admit() first ends every active session that has expired (a session is expired when now >= started + session_ttl), then moves users from the front of the queue into the active set until it holds capacity users, and returns the list admitted, in order. leave(user) removes a user from the queue or the active set (anyone else is ignored); a user who finishes buying calls it to free their place. status(user) returns ("active", None), ("waiting", position) (1 for the front of the queue) or ("absent", None), where an active user whose session has expired counts as absent. wait_estimate(user, minutes_per_session): for a waiting user, the estimated minutes to admission, ceil(position / capacity) × minutes_per_session; 0 for an active user; None otherwise.
