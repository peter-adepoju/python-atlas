Week 47, Day 1

Binary heaps

Many programs need the smallest (or largest, or most urgent) item again and again, while new items keep arriving: the next event in a simulation, the closest unvisited place on a map, the most urgent job in a queue. A sorted list makes taking the smallest cheap but adding expensive; an unsorted list is the other way round. A binary heap makes both O(log n), and finding the smallest O(1). It’s a complete binary tree stored in a list, exactly as in Week 45 Day 2, with one rule that’s much weaker than a BST’s: every parent is no larger than its children. Today you’ll build one from scratch, then learn the surprising trick that turns any list into a heap in O(n).

By the end of today you can

  • State the heap property and the shape rule, and check a list against them
  • Push with sift-up and pop with sift-down, each O(log n)
  • Turn a list into a heap in O(n) by sifting down from the last parent, and explain why it’s O(n)
  • Build max heaps and heaps ordered by a key
  • Explain what a priority queue is and why a heap suits it

Warm-up

Every value is at least as big as its parent, so the smallest value must be at the top, at index 0. That’s all a heap promises: it isn’t sorted (3 comes before 2, and 7 before 4), and that looseness is exactly what makes it cheap to keep.

The heap rules

A binary min-heap is a binary tree with two rules:

  1. Shape: it’s complete: every level is full except perhaps the last, which fills from the left. So it can live in a list with no gaps (Week 45 Day 2): the children of index i are at 2i + 1 and 2i + 2, and its parent at (i - 1) // 2.
  2. Order: every node is less than or equal to its children. So the minimum is always at index 0.
             1                 index:  0  1  2  3  4  5
           /   \               value: [1, 3, 2, 7, 4, 5]
          3     2
         / \   /               3's children: 7 and 4 (both ≥ 3)
        7   4 5                2's child: 5 (≥ 2)

A max-heap flips the order rule (every node ≥ its children), keeping the maximum at the top. Unlike a BST, a heap says nothing about left versus right: 3 is on the left of 2 here, and it could just as well have been the other way round. That’s why a heap can’t search for an arbitrary value quickly (it’s O(n)), but it doesn’t need to: its job is the minimum.

The shape rule gives a height of ⌊log₂ n⌋, always, with no rotations: a heap of a million items is 19 levels deep.

Push: sift up

To add a value, put it at the end of the list (the next free spot in the last level, so the shape stays complete). The order rule may now be broken between it and its parent, so sift it up: while it’s smaller than its parent, swap them. It stops when its parent is no larger, or it reaches the root. At most one swap per level: O(log n).

Pop: sift down

Taking the minimum is heap[0], but removing it leaves a hole at the top. Fill it with the last item (popping the end of a list is O(1), and the shape stays complete), then sift it down: while it’s larger than its smaller child, swap it with that smaller child. Swapping with the smaller one matters: it becomes the parent of the other child, so it must be the smaller of the two.

Popping everything gives the values in sorted order: that’s heap sort, which is Day 3’s topic.

Heapify in O(n)

To make a heap from n values you could push them one at a time: O(n log n). There’s a better way, published by Robert Floyd in 1964: treat the list as a complete tree already, and sift down every parent, from the last one back to the root. Leaves (the whole second half of the list) are already tiny heaps, so they need nothing; each parent, once sifted down, sits on top of two heaps and so makes a heap itself.

Why O(n)? Most nodes are near the bottom, where sifting down is short. Half the nodes are leaves (no work), a quarter sit one level up (at most 1 swap), an eighth two levels up (at most 2), and so on. The total is at most n × (1/4 + 2/8 + 3/16 + …) = n × 1, so fewer than n swaps. Pushing one at a time is the other way round: the many items at the bottom are the ones that may travel the furthest.

Priority queues

A priority queue is an abstract data type (like Week 43’s stacks and queues): you add items with priorities, and you always take out the one with the highest priority next (here, the smallest number, as in “priority 1 first”). A heap is the usual way to build one:

add look at the top take the top
unsorted list O(1) O(n) O(n)
sorted list O(n) O(1) O(1)
binary heap O(log n) O(1) O(log n)
balanced BST (Week 46) O(log n) O(log n) O(log n)

The balanced BST matches it, but the heap is simpler, uses a plain list with no node objects, and is much faster in practice. Priority queues run event simulations, schedulers, Huffman coding (Week 45), and next phase’s shortest-path algorithms.

To store items with priorities, push tuples (priority, item): tuples compare by their first element, then the second. Tomorrow covers what to do when two priorities tie and the items can’t be compared.

Key idea

A binary min-heap is a complete binary tree stored in a list (children of i at 2i + 1 and 2i + 2, parent at (i − 1) // 2) where every node is no larger than its children, so the minimum is at index 0. Push appends and sifts up, swapping with the parent while smaller; pop moves the last item to the root and sifts down, swapping with the smaller child while larger. Both are O(log n), and the height is always ⌊log₂ n⌋. Heapify sifts down every parent from the last (index n // 2 − 1) to the root, in O(n). A max-heap flips the comparisons. Heaps are the standard priority queue.

Heapify, and counting the work

Write sift_down(a, i, n) (sifting within the first n items only, comparing items with < only) and heapify(a), in place, bottom-up. Then heapify_by_pushing(a): a new list built by pushing the items one at a time with sift-up (also < only). The checks count comparisons: on 50,000 items in increasing-then-reversed orders, heapify must use fewer than 3n, while pushing reversed input needs far more.

Exercise15 points
Heaps of anything

Write Heap(key=None, largest=False): a heap ordered by key(item) (the item itself if no key), with the largest key on top when largest=True. Storing (k, item) tuples and comparing those is tempting, but two items with equal keys would then be compared themselves, and items like dicts can’t be; instead store [k, item] and compare only the keys. Methods: push, pop, peek, __len__, and pushpop(item): push then pop in one go, returning the top (if the new item would come out first, return it without touching the heap; otherwise replace the top and sift down).

Exercise10 points
More children

A d-ary heap gives each node d children: those of i are at d*i + 1 to d*i + d, and its parent is at (i - 1) // d. It’s shallower (log base d of n), so pushes are quicker, though each sift-down step compares more children. Write push(heap, v, d) and pop(heap, d) for a d-ary min-heap held in a plain list.

Bug hunt10 points
The first smaller child

This sift-down swaps with the first child that’s smaller, not the smallest, so a larger child can end up above a smaller one: this prints [2, 9, 1], which isn’t a heap. Swap with the smaller of the two children so it prints [1, 2, 9].

Bug hunt10 points
The wrong parent

This sift-up uses i // 2 for the parent, which is right for heaps that start at index 1 but wrong here: the last value, 4, is compared with 3 instead of its real parent, 5, so it stays below a larger value and the list isn’t a heap: this prints [1, 2, 5, 3, 6, 7, 4]. Use the 0-based parent so it prints [1, 2, 4, 3, 6, 7, 5].

Bug hunt10 points
Popping from the front

This pop removes the top with pop(0), which shifts every item along one place: the shape is kept, but parents and children are now different pairs, so the order rule breaks and the next pop returns the wrong value. Move the last item to the top and sift it down instead, so it prints [1, 2, 3, 4, 5, 6].

Exercise25 points
Challenge: changing a priority

Some algorithms (next phase’s shortest paths, schedulers that raise a job’s urgency) need to change the priority of an item already in the heap. A plain heap can’t find the item quickly, so keep a dict from each item to its index in the list, updated on every swap.

Write IndexedHeap (a min-heap of distinct, hashable items with numeric priorities):

  • push(item, priority) (ValueError if the item is already there), pop() returning (item, priority) (IndexError when empty), peek(), len, item in h;
  • priority(item) (KeyError if absent);
  • change(item, priority): set a new priority and sift up or down as needed, in O(log n);
  • remove(item): delete any item in O(log n) by moving the last entry into its place and sifting that entry whichever way it needs to go.

Write one _swap(i, j) that swaps entries and updates the index dict, and use it everywhere. The checks compare against a dict over thousands of random operations and verify the index dict after each one.
