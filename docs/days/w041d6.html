Forge

The first week of Phase 4 took arrays apart: how a dynamic array grows, why appends are O(1) amortised, and three patterns that make array problems fast (two pointers, sliding windows and prefix sums, with difference arrays for updates). Today’s Forge is a sensor log that uses all of them at once: readings stored in your own dynamic array, range totals in O(1), best windows, calm stretches, run counting, calibration applied to whole ranges, and a closest-pair search. The bonus is three classic problems that each need exactly one of this week’s ideas. The weekly quiz and review finish the week.

By the end of today you can

  • Build a data structure from a fixed block, and keep extra summaries up to date as it grows
  • Choose the right pattern for each question about an array
  • Combine prefix sums, windows, two pointers and difference arrays in one class
  • Check each answer against a simple, slow version

Mixed review

Exercise10 points
Rotate in place

Write rotate(nums, k), which rotates a list k places to the right in place with O(1) extra space: [1, 2, 3, 4, 5] rotated by 2 becomes [4, 5, 1, 2, 3]. k may be bigger than the length, or 0; an empty list stays empty. Use the reversal trick: reverse the whole list, then reverse the first k items and the rest separately, each with two pointers (no slicing to make new lists, and no reverse()).

Exercise10 points
Moving averages

Write moving_averages(values, k): the average of every window of k neighbouring values, in order, each rounded to 2 decimal places, in O(n) with a sliding total. k must be from 1 to len(values), else ValueError.

Forge: a sensor log

A weather station records one whole-number reading a minute. Volunteers ask questions about the log, and occasionally correct whole stretches of it after finding that a sensor was off. Build SensorLog, which answers every question quickly, even with hundreds of thousands of readings.

Storage. Readings go into your own dynamic array: a fixed block made with [None] * capacity, starting at capacity 1 and doubling when full, never appended to. Keep resizes (how many times the block grew) and a read-only property capacity. Keep prefix sums up to date as readings arrive, so range totals never need a loop.

  • add(value) stores a reading; len(log) is how many there are; log[i] reads one (negative indexes count from the end; out of range raises IndexError).
  • total(i, j): the sum of readings i to j - 1, in O(1). i and j must satisfy 0 <= i <= j <= len, else IndexError.

Questions.

  • best_window(k): the busiest k consecutive minutes, as (start, total); earliest on a tie. ValueError if k isn’t from 1 to len.
  • longest_between(lo, hi): the longest run of consecutive readings all from lo to hi inclusive, as (start, end) (half-open, earliest on a tie), or None if no reading is in range.
  • count_totals(k): how many runs of consecutive readings (length 1 or more) add up to exactly k. Readings may be negative.
  • closest_pair(target): two different readings (at different positions) whose sum is closest to target, as (a, b) with a <= b; on a tie, the smaller sum. Use a sorted copy and two pointers. Fewer than 2 readings raises ValueError.

Corrections. calibrate(corrections), where each correction is (i, j, delta): add delta to every reading from i to j - 1. Apply them all at once with a difference array in O(n + number of corrections), then bring the prefix sums back up to date (once, not once per correction).

The checks compare every answer with a simple, slow version on random data, and time the big cases.

Exercise50 points
Forge: a sensor log

Write SensorLog to the specification above.

Paying in advance

Look at where SensorLog spends its time. Each add does a little extra work (one addition for the prefix sums, and occasionally a resize); in return, every total is instant, and best_window and count_totals never add up a range. calibrate is the one operation that disturbs the summary, so it rebuilds it once, at a cost of O(n), rather than patching it after every correction. That’s the trade at the heart of data structure design: decide which operations must be fast, and pay for them, in advance or in memory, out of the operations that can afford it.

Forge bonus: three classics

Exercise30 points
Forge bonus: three classics

Each of these is a well-known problem with a neat O(n) answer using one of this week’s ideas. Write all three.

  1. max_profit(prices): you may buy once and later sell once. Return the largest profit possible (0 if prices only fall). Keep the lowest price seen so far as you go: one pass, O(1) space.
  2. products_below(nums, k): for a list of positive whole numbers, how many runs of consecutive items have a product less than k. Use a variable window: at each end, shrink while the product is at least k, and every run ending at end that starts at or after start counts.
  3. start_station(petrol, cost): petrol stations stand in a circle; at station i you can fill up petrol[i] litres, and driving on to the next station uses cost[i]. Starting with an empty tank, return the station from which you can drive all the way round, or -1 if there’s none (when there is one, it’s the only one). Hint: if the total petrol is less than the total cost, it’s impossible; otherwise, whenever the running tank goes negative, no station from the current start up to here can work, so start again from the next one.
