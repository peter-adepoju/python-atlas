## Warm-up

:::predict
TRANSITIONS = {
    ("locked", "coin"): "unlocked",
    ("unlocked", "push"): "locked",
}

state = "locked"
for event in ["push", "coin", "coin", "push", "push"]:
    new = TRANSITIONS.get((state, event), state)
    print(f"{state:8} + {event:4} -> {new}")
    state = new
:::

A coin-operated turnstile can be **locked** or **unlocked**, and the same event means different things in each: a push does nothing when it's locked, and lets you through (locking it again) when it's unlocked. The whole behaviour fits in a table of `(state, event) -> next state`. That's a **state machine**, and today is about writing them cleanly.

## Behaviour that depends on state

Here's how state-dependent classes usually start:

```python
class Order:
    def pay(self):
        if self.status == "placed":
            self.status = "paid"
        elif self.status == "paid":
            raise ValueError("already paid")
        elif self.status == "cancelled":
            raise ValueError("cancelled orders can't be paid")
        ...

    def ship(self):
        if self.status == "paid":
            ...
        elif self.status == "placed":
            ...
```

Every method has the same `if` chain on the status, and every new status (`"refunded"`, `"on hold"`) means editing every method. The rules for one status are scattered across all of them, and it's easy to forget a case. The **State** pattern (Gang of Four: "allow an object to alter its behaviour when its internal state changes; the object will appear to change its class") gathers each state's rules into one place.

## The State pattern

Each state is a class with a method for each event. The object that has a state (the **context**) holds the current state object and passes each event to it; the state decides what happens and which state comes next:

:::example
class Locked:
    name = "locked"
    def coin(self, gate):
        gate.state = Unlocked()
        return "unlocked: walk through"
    def push(self, gate):
        return "locked: insert a coin"

class Unlocked:
    name = "unlocked"
    def coin(self, gate):
        gate.refunds += 1
        return "already open: coin returned"
    def push(self, gate):
        gate.state = Locked()
        gate.passed += 1
        return "thank you"

class Turnstile:
    def __init__(self):
        self.state = Locked()
        self.passed = 0
        self.refunds = 0

    def coin(self):
        return self.state.coin(self)

    def push(self):
        return self.state.push(self)

t = Turnstile()
for event in ["push", "coin", "coin", "push", "push"]:
    print(f"{event}: {getattr(t, event)()}  (now {t.state.name})")
print(t.passed, t.refunds)
:::

- Everything about being locked is in `Locked`; everything about being unlocked is in `Unlocked`. Adding a state (say `Broken`, where every event says "out of order") is one new class.
- The context, `Turnstile`, has no `if` on its state at all; it just passes events on.
- States change the context (`gate.state = Unlocked()`), so they're passed the context as an argument.

States that hold no data of their own, like these, can be shared: one `Locked` object would do for every turnstile. When a state does need data (how many coins have been put in so far, say), it can keep it, or the context can.

## A table of transitions

When the states differ mostly in **which events are allowed and where they lead**, rather than in complicated behaviour, a **transition table** is simpler than a class per state. It's a dictionary from `(state, event)` to the next state, usually with an Enum for the states (Week 32):

:::example
from enum import Enum

class Status(Enum):
    PLACED = "placed"
    PAID = "paid"
    SHIPPED = "shipped"
    DELIVERED = "delivered"
    CANCELLED = "cancelled"

MOVES = {
    (Status.PLACED, "pay"): Status.PAID,
    (Status.PLACED, "cancel"): Status.CANCELLED,
    (Status.PAID, "ship"): Status.SHIPPED,
    (Status.PAID, "cancel"): Status.CANCELLED,
    (Status.SHIPPED, "deliver"): Status.DELIVERED,
}

class Order:
    def __init__(self, code):
        self.code = code
        self.status = Status.PLACED
        self.history = [Status.PLACED]

    def handle(self, event):
        key = (self.status, event)
        if key not in MOVES:
            allowed = sorted(e for (s, e) in MOVES if s is self.status)
            raise ValueError(f"can't {event} a {self.status.value} order; allowed: {allowed}")
        self.status = MOVES[key]
        self.history.append(self.status)

o = Order("A17")
for event in ["pay", "ship", "cancel"]:
    try:
        o.handle(event)
    except ValueError as err:
        print("ValueError:", err)
print([s.value for s in o.history])
:::

The table is **data**: the whole life of an order is visible in five lines, it can be printed as documentation, checked by tests ("can every state reach the end?"), or even drawn as a diagram. The `allowed` list in the error message comes straight from it.

Tables can also hold an **action** to run on each transition, as a function: `(Status.PAID, "ship"): (Status.SHIPPED, send_tracking_email)`.

## Choosing

| Use | When |
|---|---|
| a plain Enum with one or two `if`s | a couple of states and very little behaviour depends on them |
| a transition table | the main question is "which events are allowed, and where do they lead?" |
| state classes | each state behaves quite differently, with real logic per state and event |

You'll often combine them: a table for the transitions and a small function per transition for the actions. Whichever you choose, keep two rules: **every event in every state has a defined result** (even if that result is "not allowed"), and **the state can only change through the machine**, never by code elsewhere setting `order.status` directly.

:::key
State (Gang of Four): when an object's behaviour depends on its state, give each state its own object with a method per event; the context passes events to its current state, which acts and chooses the next state, replacing `if status == ...` chains in every method. A transition table, a dictionary from `(state, event)` to the next state (often with Enum states), is simpler when states differ mainly in what's allowed; it's data you can print and test. Reject events that aren't allowed with a clear error listing what is, and let the state change only through the machine.
:::

:::exercise id=machine points=15 title="A vending machine's states"
Write a vending machine with the State pattern. `Machine(price)` has `insert(pence)`, `choose()` and `refund()`, each returning a message, and `credit` and `dispensed` attributes. It passes each event to its state object (`Idle`, `HasCredit` or `SoldOut`):

Each state class has `insert(self, m, pence)`, `choose(self, m)` and `refund(self, m)`, and changes `m.state` when needed. `Machine.__init__` can choose the first state with a conditional expression rather than an `if` statement: `self.state = SoldOut() if stock == 0 else Idle()`.
@@solution
class Idle:
    def insert(self, m, pence):
        m.credit += pence
        m.state = HasCredit()
        return f"credit {m.credit}"

    def choose(self, m):
        return "insert money first"

    def refund(self, m):
        return "nothing to refund"

class HasCredit:
    def insert(self, m, pence):
        m.credit += pence
        return f"credit {m.credit}"

    def choose(self, m):
        if m.credit < m.price:
            return f"need {m.price - m.credit} more"
        change = m.credit - m.price
        m.credit = 0
        m.dispensed += 1
        m.stock -= 1
        m.state = SoldOut() if m.stock == 0 else Idle()
        return f"enjoy! change {change}"

    def refund(self, m):
        amount, m.credit = m.credit, 0
        m.state = Idle()
        return f"refunded {amount}"

class SoldOut:
    def insert(self, m, pence):
        return "sold out"

    def choose(self, m):
        return "sold out"

    def refund(self, m):
        if m.credit == 0:
            return "nothing to refund"
        amount, m.credit = m.credit, 0
        return f"refunded {amount}"

class Machine:
    def __init__(self, price, stock=10):
        self.price = price
        self.stock = stock
        self.credit = 0
        self.dispensed = 0
        self.state = SoldOut() if stock == 0 else Idle()

    def insert(self, pence):
        return self.state.insert(self, pence)

    def choose(self):
        return self.state.choose(self)

    def refund(self):
        return self.state.refund(self)

:::exercise id=reachable points=15 title="Checking a table"
Because a transition table is data, it can be checked. Write `allowed(table, state)` (the events allowed in a state, sorted), `reachable(table, start)` (every state reachable from `start` by any sequence of events, including `start`, as a set) and `dead_ends(table, start, finals)` (the reachable states that aren't in `finals` and have no events at all, sorted). States and events are strings.
@@starter
___
@@tests
def test_checks():
    "checking a machine"
    T = {("draft", "submit"): "review", ("review", "approve"): "published", ("review", "reject"): "draft",
         ("published", "archive"): "archived", ("review", "lose"): "limbo", ("ghost", "x"): "draft"}
    assert allowed(T, "review") == ["approve", "lose", "reject"] and allowed(T, "archived") == []
    assert reachable(T, "draft") == {"draft", "review", "published", "archived", "limbo"} and reachable(T, "archived") == {"archived"}
    assert dead_ends(T, "draft", {"archived"}) == ["limbo"] and dead_ends(T, "draft", {"archived", "limbo"}) == []
@@hint
`reachable` is a search like Week 32's flood fill: keep a set of seen states and a list to visit, and from each state follow every `(state, event)` entry that starts there.
@@solution
def allowed(table, state):
    return sorted(e for (s, e) in table if s == state)

def reachable(table, start):
    seen = {start}
    todo = [start]
    while todo:
        s = todo.pop()
        for (frm, _), to in table.items():
            if frm == s and to not in seen:
                seen.add(to)
                todo.append(to)
    return seen

def dead_ends(table, start, finals):
    return sorted(s for s in reachable(table, start) if s not in finals and not allowed(table, s))
:::

:::exercise id=actions points=15 title="Transitions with actions"
Write a class `Ticket` for a help-desk ticket, whose transition table `FLOW` maps `(state, event)` to `(next_state, action)`, where an action is a function taking the ticket. The states are `"open"`, `"assigned"`, `"resolved"` and `"closed"`. Events: from open, `"assign"` (to assigned; the action records the time of the change: increment `ticket.changes` and append `"assigned"` to `ticket.log`); from assigned, `"resolve"` (to resolved; log `"resolved"`) and `"unassign"` (back to open; log `"unassigned"`); from resolved, `"reopen"` (to assigned; log `"reopened"`) and `"close"` (to closed; log `"closed"`). Every action also adds 1 to `ticket.changes`. `Ticket.handle(event)` raises `ValueError` for events not in the table, and otherwise changes the state and runs the action.
@@starter
___
@@tests
def test_ticket():
    "actions"
    T = ns["Ticket"]
    t = T()
    for e in ["assign", "resolve", "reopen", "resolve", "close"]:
        t.handle(e)
    assert t.state == "closed" and t.log == ["assigned", "resolved", "reopened", "resolved", "closed"] and t.changes == 5
    for e in ["reopen", "assign"]:
        try:
            t.handle(e)
            assert False, f"{e} on a closed ticket should raise ValueError"
        except ValueError:
            pass
    assert t.changes == 5 and all(callable(a) for _, a in FLOW.values()) and len(FLOW) == 5
@@hint
A helper that makes actions saves repetition: `def logs(word): return lambda t: (t.log.append(word), ...)`, or a small named function per word made in a loop.
@@solution
def logs(word):
    def action(ticket):
        ticket.log.append(word)
        ticket.changes += 1
    return action

FLOW = {
    ("open", "assign"): ("assigned", logs("assigned")),
    ("assigned", "resolve"): ("resolved", logs("resolved")),
    ("assigned", "unassign"): ("open", logs("unassigned")),
    ("resolved", "reopen"): ("assigned", logs("reopened")),
    ("resolved", "close"): ("closed", logs("closed")),
}

class Ticket:
    def __init__(self):
        self.state = "open"
        self.log = []
        self.changes = 0

    def handle(self, event):
        key = (self.state, event)
        if key not in FLOW:
            raise ValueError(f"can't {event} a ticket that is {self.state}")
        self.state, action = FLOW[key]
        action(self)

from enum import Enum

class Role(Enum):
    WRITER = "writer"
    EDITOR = "editor"
    LEGAL = "legal"

WORKFLOW = {
    ("draft", "submit"): ("review", {Role.WRITER}),
    ("review", "request_changes"): ("draft", {Role.EDITOR}),
    ("review", "approve"): ("legal_check", {Role.EDITOR}),
    ("legal_check", "clear"): ("scheduled", {Role.LEGAL}),
    ("legal_check", "block"): ("draft", {Role.LEGAL}),
    ("scheduled", "publish"): ("published", {Role.EDITOR}),
    ("scheduled", "pull"): ("review", {Role.EDITOR, Role.LEGAL}),
}

class Article:
    def __init__(self, title):
        self.title = title
        self.state = "draft"
        self.history = []

    def handle(self, event, role):
        key = (self.state, event)
        if key not in WORKFLOW:
            allowed = sorted(e for (s, e) in WORKFLOW if s == self.state)
            raise ValueError(f"can't {event} when {self.state}; allowed: {allowed}")
        next_state, roles = WORKFLOW[key]
        if role not in roles:
            raise PermissionError(f"{role.name.lower()} can't {event}")
        self.state = next_state
        self.history.append((next_state, event, role))

    def next_steps(self, role):
        return sorted(e for (s, e), (_, roles) in WORKFLOW.items() if s == self.state and role in roles)

def path_exists(start, end):
    seen = {start}
    todo = [start]
    while todo:
        s = todo.pop()
        if s == end:
            return True
        for (frm, _), (to, _) in WORKFLOW.items():
            if frm == s and to not in seen:
                seen.add(to)
                todo.append(to)
    return False
